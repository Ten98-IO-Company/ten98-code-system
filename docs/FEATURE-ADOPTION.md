# Adopt a complete feature

Start with [the feature catalogue](../features/catalog.json) and the canonical `databasePolicy` in [architecture.json](../architecture.json). New stateful Node applications default to PostgreSQL with Drizzle and checked TypeScript; stateless packages need no database. Discover supplies the default framework, identity and feature source on PostgreSQL, Drizzle and pg-boss. Campaign also runs PostgreSQL and Drizzle; its retained identity and routing adapters have separate adoption gaps. Native Cloudflare D1 is an explicit platform exception; other nondefault engines require a recorded purpose and review. Connect is not built yet.

The catalogue retains `defaultAuthenticatedNodeStack` as its framework-source selector for compatibility; database choice comes from the canonical policy. The engine in an existing app is not the default for a new application.

Each catalogue `sources` entry names the app's current release tag. Check out that tag in a fresh working folder, install through its lockfile with Node 24 and the app's own package manager, and run its listed checks before adopting anything. It is a complete reference to adopt into the same stack, not a drop-in package:

```sh
git clone --depth 1 --branch v0.7.4 https://github.com/Ten98-IO-Company/ten98-discover.git work/ten98-feature-reference
```

Entry-point paths in the catalogue are navigation aids, not a list of independently copyable files. A tag carries the complete source closure: routes, UI, controllers, schema and migrations, jobs, public configuration examples, lockfiles, pinned runtime and UI archives, tests, licences and notices. The 2026-10-20 source bundles are archived history and predate Campaign on PostgreSQL, Amazon SES and account closure.

Use imports for `@ten98/runtime` primitives and `@ten98/ui` presentation. A URL validator is not OIDC sign-in; a transport wrapper is not a paid-work lifecycle; a grant predicate is not transactional tenant authorization. Follow the catalogue's full source reference when adopting those features.

The Shopify crawler-access mechanism in the 0.21.0 source candidate provides `parseShopifyCrawlerAccess`, `shopifyCrawlerHeadersFor` and `verifyShopifyCrawlerAccess`. Import those functions instead of copying signature parsing, expiry or header selection into an app. The helper performs no key lookup or network request: the owning app supplies a public verification key and retains domain proof, encrypted credentials, current authorization, revision binding, request recovery, scheduling and safe crawl transport. Selecting headers is not authorization to crawl. Recheck a selected credential after waits and before native dispatch; expired, revoked or unreadable selected access must stop its request. The pinned upstream MIT attribution is in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md). Track complete consumer adoption and remaining live-provider/release checks in [issue102](https://github.com/Ten98-IO-Company/ten98-code-system/issues/102); a local archive is not a published release.

The 0.22.0 source candidate promotes Discover's `addressKey` and `publicNetworkAddress` policy, plus `pinnedNetworkPeer` and bounded, cancellable dual-family `resolveNetworkHost`. Import these mechanisms without creating another app-local address policy. DNS results are evidence, not admission: reject the whole set if any target is nonpublic, pin an admitted address and verify the connected peer before forwarding. Applications still own URL scope, authority and transport. `normalizeLighthouseReport` consumes the pinned local Lighthouse 13.6.0 navigation report, binds its requested URL, and projects bounded scores, lab measurements and audit details with explicit missing/error/truncation evidence. It performs no browser or provider work. Track actual imports, removal of duplicates, real isolated-browser acceptance and remaining release work in [issue 103](https://github.com/Ten98-IO-Company/ten98-code-system/issues/103); package tests alone do not establish a working renderer.

For stack-bound features, first run the unmodified reference with its own documented setup and tests. Then trace the caller through route admission, session/token identity, authorization, validation, transaction, provider boundary, receipt and rendered outcome. Adopt the complete flow into the same supported stack or make a controlled adaptation with explicit migrations and compatibility tests. Copying one handler while omitting its schema, lock, worker or authority recheck is incomplete.

Record the source repository and tag, the commit, the source path and the reason for adaptation beside copied code or in the consuming change. Retain copyright and notices. Link the owning code-system GitHub issue and identify who will port later fixes. Prefer improving the maintained canonical implementation and adopting that version together; do not establish independently evolving auth/provider frameworks.

Verification must include the feature's listed tests and actual UI/API/persistence path, plus relevant negative cases: wrong tenant/role, revocation after a wait, expired/reused capability, malformed/incomplete response, failed transaction, stale draft, unmount/navigation, keyboard/narrow layout and uncertain provider outcome. Run network/provider scenarios only in approved isolated fixtures. Synthetic checks are evidence for their fixture scope; they establish no live-provider certification or production deployment.

Before claiming adoption complete, preserve existing accounts/data and error contracts, pass the consumer's architecture/type/test/build gates, obtain independent review, and record the exact source tag and commit, commands, results, skips and remaining gaps in GitHub. The catalogue's issue statuses are a snapshot: consult issues [#4](https://github.com/Ten98-IO-Company/ten98-code-system/issues/4) through [#8](https://github.com/Ten98-IO-Company/ten98-code-system/issues/8) before choosing a reference. Current static dependency checks do not prove complete feature adoption.

## Row-level security with Drizzle

Every app forces row-level security and connects as a non-owner role without BYPASSRLS. Declare what Drizzle can carry in the schema and put the rest in a custom migration step (`drizzle-kit generate --custom`); the migration ledger applies both kinds of file the same way. Trial on drizzle-orm 0.45.2 and drizzle-kit 0.31.11 against PostgreSQL 18.6, 2026-11-14:

- In the schema: `pgPolicy(name, { as, for, to, using, withCheck })` in the table callback, `.enableRLS()` on a table without a policy (a policy enables RLS by itself), and `pgRole(name).existing()` to name the application role in `to`. drizzle-kit emits `ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` with the `sql` expression verbatim, and a second generate reports no change.
- In the custom step: `FORCE ROW LEVEL SECURITY`, every `GRANT`, the roles themselves (`pgRole` has no LOGIN, BYPASSRLS or password options), triggers and functions. drizzle-kit keeps no record of these, so it neither generates nor reverts them.
- Review generated SQL. A policy change is emitted as `DROP POLICY` then `CREATE POLICY`. drizzle-kit writes `WITH CHECK` on a `for: 'select'` or `for: 'delete'` policy, which PostgreSQL rejects. Removing `.enableRLS()` from a table without a policy emits `DISABLE ROW LEVEL SECURITY`, which leaves FORCE set but switches the protection off.

`@ten98/runtime/tenancy` carries this split: `createTenancy({ setting, column, tables })` returns `policy(name)` for each scoped table's Drizzle callback, `forceRowLevelSecurity()` for the custom step, `withWorkspace` and `withWorkspaces` for scoped Drizzle transactions, and `assertDatabaseRoles` for start-up. Grants and roles stay in the app's custom step. `@ten98/runtime/db` provides the pool, the int8 and DATE parsers, the one-pool-per-process slot, the team tables and `transaction(db, run)`.

The scope is set only by the tenancy helpers, after the membership check; there is no public setter. Database guard tests that must act as the application role with an arbitrary scope import `setScopeForTesting(client, tenancy, workspaceIds)` from the separate `@ten98/runtime/tenancy/testing` entry, on a connection and transaction the test owns. It accepts UUIDs only. The architecture check refuses an import of it from a file under the app's data roots, so only tests outside them should use it. The check matches text: it catches `from '…'`, a bare `import '…'`, and `import('…')` or `require('…')` with a literal specifier. It does not catch a runtime-built specifier, a path alias, a re-export from outside the roots, the deep `node_modules/…/tenancy-testing.mjs` path, `createRequire(…)`, or a comment before the specifier. Review imports of this entry like any other test-only code. Read access (`'read'` and every `withWorkspaces`) switches its own transaction to READ ONLY once the membership row is share-locked, so a write in a read callback fails with SQLSTATE 25006. Inside a caller's transaction (`outer`, or a transaction passed as `db`, which runs a savepoint) the caller keeps its access mode and gets its own scope back when the inner call returns or throws. PostgreSQL refuses the share lock inside a READ ONLY transaction, so a nested call there fails closed.

- **What it admits:** only memberships of the same user that the transaction's own top-level helper call share-locked, and a removal must wait for those. That check is the transaction's first statement, so no savepoint or ROLLBACK TO can release it.
- **The record lasts only for its transaction.** A transaction object used after its transaction ended, for example by an un-awaited nested call, is refused. So is a nested call after the caller issued its own ROLLBACK and BEGIN inside the helper's transaction. The record is tied to that transaction's `transaction_timestamp()`. Issuing transaction control yourself inside a helper transaction is unsupported.
- **Nested locks are never counted.** A rollback the helper cannot see could release them. So a membership that a nested write call locked is still refused by a later nested read, after the caller has set READ ONLY.
- **Everything else is refused.** That includes another user's membership of the same workspace, any workspace in a READ ONLY transaction the caller opened itself, and any call given a Drizzle savepoint the caller opened itself, even when the lock is held. These throw `UnlockedScopeError` (`code: 'TENANCY_SCOPE_UNLOCKED'`). Map it as a programming error, not a missing workspace.
- **To nest reads across workspaces**, open the outer call for the same user over all of them (`withWorkspaces`), or make it a write call. Await nested calls on one transaction in turn: run at once (`Promise.all`), their scopes and restores interleave, and a callback can see the other call's workspace, though never one outside the user's memberships. Before an app adopts read-only reads, check that no read callback writes (audit or last-seen rows, for example).

Known upstream issue: drizzle-orm 0.45.2's node-postgres `transaction` sends BEGIN before its `try`, so a failed BEGIN never releases the pooled connection, and a failed ROLLBACK replaces the error that caused it. `transaction(db, run)` from `@ten98/runtime/db`, which the tenancy helpers use, checks the connection out itself over a pool and runs BEGIN, COMMIT and ROLLBACK itself. It always releases the connection, discards it when BEGIN, COMMIT or ROLLBACK failed, and rethrows the callback's own error, or a failed COMMIT's. A COMMIT that the server refuses for a constraint or a serialisation failure also discards a connection that was still usable. That costs a reconnect and nothing else. A config that sets nothing (`{}`) sends no `SET TRANSACTION`. Use it in place of `db.transaction`. A pg client checked out of a pool has no `error` listener of its own, so a backend the server terminates mid-transaction (a failover, `pg_terminate_backend`) crashes the process under plain `db.transaction`; `transaction(db, run)` listens for the checkout's lifetime and discards that connection instead. A transaction (a savepoint), or a database on a single client, uses Drizzle's own `transaction`. A single client means a `pg.Client` from the same copy of pg; a pool's checked-out client is one. Any other database is refused with a TypeError instead of falling back silently. That includes one from a second copy of drizzle-orm or pg, and any wrapper object, whatever its shape, because statements through a wrapper could run on different backends.
A transaction a failed statement aborted answers COMMIT with ROLLBACK and no error, for example when a callback catches the error of one of its statements and goes on. `transaction(db, run)` checks the COMMIT tag and then throws `TransactionRolledBackError` (`code: 'TRANSACTION_ROLLED_BACK'`) instead of returning the callback's result, so a rolled-back transaction is never reported as success. Run a statement that may fail and should not end the transaction in a savepoint (`tx.transaction(…)`). This holds on a database over one pg `Client` (as `getAuth(client)` uses) as well as over a pool: there too `transaction(db, run)` issues BEGIN and COMMIT itself and leaves the client to its owner. Such a client must serve one request at a time: two transactions interleaved on one client share one backend, so their locks exclude nothing and either can commit or roll back the other's statements. 0.29.0 note: a test double whose COMMIT result has no `command` field now makes every `transaction()` throw; make the double answer COMMIT with `command: 'COMMIT'`, as PostgreSQL does.

Application queries are typed Drizzle queries. The architecture check counts raw statements in each app's data roots against the app's committed `raw-statements.json`, and refuses any file whose count rises. It counts:
- pg `.query(`, also written `?.(`, `!(`, `?.<T>(`, `['query'](`, `.query.call(`, `.apply(` or `.bind(`, with comments allowed before the type argument or the parenthesis;
- `sql.raw(`;
- `.execute(` given SQL text, a `sql` template or `sql.join(`, also inside extra parentheses or after a comment.

Each form counts with or without a type argument, with `sql` under any imported name, including the namespace in `import * as d` and `import d, * as ns`.

The check matches text, so a comment or an unrelated `.query(` method is counted. So is a comparison that reads like a type argument, as in `a.query! < b && c > (d)`. These forms are not counted:
- a statement passed to `.execute(` by variable, or as a conditional (`cond ? sql… : sql…`);
- `sql.empty()`;
- `String.raw` text given to `.execute(`;
- a statement reached through a computed key or a destructured `query`;
- `(pool.query)(`;
- `sql` re-exported through an app module, or taken from a dynamic `import()` under another name (`sql` itself is always counted);
- `sql.raw` taken into a variable;
- a type argument with `>` inside a string literal.

Each allowlist entry is `"path": { "count": n, "reason": "…" }`, and the check refuses an entry without a reason. `node node_modules/@ten98/runtime/check.mjs --update-raw-statement-baseline .` records the first allowlist with empty reasons, which fail until someone writes why each file's statements cannot be typed queries; afterwards it only lowers counts and keeps the reasons. The allowlist counts per file, so replacing one raw statement with another in a listed file passes the check and shows only when the diff is reviewed. The runtime is held to the same rule; its own allowlist names the tenancy statements that are raw by necessity (the policy DDL, set_config and the catalogue check), the migration ledger and the team controller.

## Environment configuration

`@ten98/runtime/config` replaces app-local `environmentValue` and `secret` helpers. `readEnvironment(name, env)` returns `NAME`, or the trimmed contents of the file `NAME_FILE` names (a Compose secret), refuses both set at once, and returns undefined when neither is set. As in discover and books, the checks are truthy: an empty `NAME_FILE` is unset and an empty `NAME` never conflicts, but with no file `NAME` comes back unchanged, untrimmed and `''` included. `readSecret(name, { minimumLength = 32, env })` refuses a missing or short secret. `loadConfig(zodObject, env)` reads each schema key that way and parses the strings with zod (use `z.coerce` for numbers), leaving out empty values so `.default()` applies, reporting every failing key in one error with `code: 'CONFIG_INVALID'` and `keys`; messages name keys and never carry values or file paths. Deliberate change from the apps: an unreadable `NAME_FILE` throws that ConfigError (`NAME_FILE names a file that cannot be read (ENOENT)`) instead of the raw fs error with its path. An app that mapped `ENOENT` or `EACCES` from configuration to a 503 (discover's `api.ts:1383`) maps `code: 'CONFIG_INVALID'` instead, in the same change that adopts this entry. `loadConfig` needs the optional `zod` 4.6.6 peer; the readers need nothing. Each app keeps its own `getConfig`. Campaign's generated `DATA_DIR/session-secret` is read with `SESSION_SECRET_FILE` pointing at that file or at a Compose secret, so existing sessions stay valid.

## Presentation ratchet

Apps whose profile has a `presentation` policy keep a committed `presentation-baseline.json`. The architecture check parses each file under the policy's roots and refuses any file whose count rises for a rule: `element` (host tags), `styling` (`className` and `style`), `inner-html`, `create-element` and `stylesheet`. `node node_modules/@ten98/runtime/check.mjs --update-presentation-baseline .` lowers the baseline as screens move onto `@ten98/ui`, and refuses to record a rise. Known limit: `element` counts lowercase host tags, namespaced tags and member tags whose root is not a `@ten98/ui` import. It never counts a capitalised component, whether it comes from `@ten98/ui` or from the app, so it measures host tags and styling, not whether a component comes from the design system. Raw HTML moved into an app-local component is still counted in that component's own file.

## OpenRouter Chat Completions protocol

`readOpenRouterAssistantMessageV1(message, finishReason, options)` validates the complete assistant message before exposing calls. Results distinguish `text`, `refusal`, `tool-calls` and `incomplete`; only `tool-calls` is executable protocol evidence. Length, content-filter and error termination remain incomplete. Unknown terminal states or malformed calls reject the whole message with a fixed TypeError.

`validateOpenRouterToolHistoryV1(history, options)` accepts text system/user messages, assistant messages and complete tool-result groups. Systems precede users, assistants follow a user, every call has exactly one matching result before another conversation message, and optional result names match. IDs are unique within each call group and may recur after that group completes. Orphan, duplicate, missing and interleaved results fail.

Options require `allowedToolNames`, `maxContextBytes`, `maxArgumentBytes` and `maxMessageBytes`; an application may explicitly select 131072, 8192 and 2097152 bytes respectively. Bounds use UTF-8 bytes, include tool outputs and reasoning, and reject rather than truncate. Arguments must encode a JSON object; their original string is preserved exactly. Ordered reasoning details, signatures and unknown JSON block fields are retained without interpretation. Outputs are detached from input mutation. Unsupported fields, non-JSON objects, cycles, accessors, NUL and malformed Unicode fail.

These pure helpers perform no I/O and do not parse the response envelope. The app still owns bounded envelope reading, HTTP/choice/model checks, usage, tool definitions, dispatch authorization, tenancy, credential revisions, idempotency, persistence and recovery. Passing a history or receiving a call is not permission to execute it. These helpers do not constitute complete assistant adoption; consumer and live-provider acceptance remain outstanding.

## Exact money arithmetic

Runtime 0.26.0 adds `parseMoney`, `formatMoney`, `addMoney`, `subtractMoney`, `compareMoney`, `multiplyMoney`, `percentOfMoney`, `allocateMoney`, `assertMoneyInRange`, `MONEY_MIN`, `MONEY_MAX` and the `MoneyExponent` and `MoneyRounding` types to both `@ten98/runtime` and `@ten98/runtime/browser`. Amounts are bigint minor units for a currency exponent of 0, 2 or 3; nothing converts to a Number or uses floating point. Import these functions instead of writing another app-local decimal or rounding helper.

`parseMoney` is the wire boundary: it refuses grouping, exponent notation, more fraction digits than the exponent and any amount outside the PostgreSQL `bigint` range (`MONEY_MIN` to `MONEY_MAX`). Arithmetic does not bound its results, so call `assertMoneyInRange` on every computed amount (a total, a converted or taxed amount, an allocation part) before persisting it. `multiplyMoney` and `percentOfMoney` round `half-up`, `half-even` or `down`, symmetrically in sign; `allocateMoney` always sums to the total.

The next release adds `convertMoney(amount, fromExponent, rate, toExponent, rounding)` and `rateOfAmounts(target, targetExponent, source, sourceExponent, places, rounding)` for multi-currency lines. A conversion rate is target units per source unit, above zero, with at most 10 fraction digits; a derived rate has exactly `places` digits (0 to 10) and is refused only for a zero source. Each function rounds once on exact integers, so a PostgreSQL guard recomputes the same result with the `div(numeric, numeric)` function on `numeric` integers, never `numeric` division followed by `round`. PostgreSQL has no `div` operator, and `10 ^ b` on integer literals is double precision, so write powers as `power(10::numeric, b)`. `div` truncates toward zero, so apply it to absolute values and restore the sign; the plain form is exact only for positive amounts. With `F` the source amount, `B` the target amount, `R` the rate's integer units, `p` its places and `f`, `b` the exponents, half-up is:

```sql
-- Rate entered: the converted amount.
sign(F) * div(2 * abs(F) * R * power(10::numeric, b) + power(10::numeric, p + f), 2 * power(10::numeric, p + f))
-- Base entered: the derived rate's integer units.
sign(B) * sign(F) * div(2 * abs(B) * power(10::numeric, p + f) + abs(F) * power(10::numeric, b), 2 * abs(F) * power(10::numeric, b))
```

Converting back at a derived rate drifts by at most `F × 10^(b − f − p) / 2` units before rounding. Amounts of opposite sign give a negative derived rate, which `convertMoney` refuses, so check a derived rate before converting with it. Results are not range-checked, a derived rate of zero is returned, and the application owns its rate column's precision, its refusal messages and `assertMoneyInRange` on every converted amount before storing it.

The application still owns its zod wire schema (accept a decimal string, then parse), JSON serialization of bigint values, the `pg` int8 type parser that returns bigint instead of a string or Number, currency selection, display locale, which rounding mode and level a tax rule needs (per line or per document), ledger postings and their transactions. These helpers perform no I/O. Package tests do not establish consumer adoption; record each consumer's imports and checks in its adoption issue.

## Transactional email

Runtime 0.28.0 adds `@ten98/runtime/email`, extracted from discover's and books' `src/server/email.ts`. `sendTransactionalEmail({ to, subject, text }, { env, isSuppressed })` sends one plain-text message (the HTML part is generated from `text`) to one bare mailbox in one attempt, within 15 seconds for the whole send, and resolves `{ accepted: true, delivery: 'unconfirmed' }`: the provider accepted it, nothing more. Every failure, disabled or bad configuration, refused input and a suppressed recipient included, is the same `EmailDeliveryError` with `status` 503 and a fixed message; nothing is logged and no provider error or message content is attached. Input is strict: `to` is one bare mailbox, `subject` at most 200 characters with no control or separator characters, `text` at most 65,536 UTF-8 bytes, and no other fields. `isSuppressed` is required, so no call site sends unchecked by omission. It is either the app's own lookup, `(address) => boolean | Promise<boolean>`, which runs before every transport, or the literal `false` for an app that keeps no suppression list. Only an explicit `false` from the lookup lets the message go; `true`, `undefined`, any other value, a throw or a rejection refuses the send. Missing or `null` options refuse the same way. `getEmailStatus(env)` never throws; read `.configured`. SMTP counts as configured only when the optional `nodemailer` peer is installed. `withEmailTransportsForTests({ fetch, smtp }, action)` substitutes the provider fetch and the SMTP sender inside `action` only.

`EMAIL_TRANSPORT` is `disabled` (the default), `ses`, `cloudflare` or `smtp`, and every setting is read through `readEnvironment`, so each accepts `_FILE`. `EMAIL_FROM` is a bare mailbox. SES uses `sendSesEmail` with `EMAIL_SES_REGION` (one of `SES_REGIONS`), `EMAIL_SES_ACCESS_KEY_ID`, `EMAIL_SES_SECRET_ACCESS_KEY` and an optional `EMAIL_SES_CONFIGURATION_SET`. Cloudflare uses `sendCloudflareEmail` with `EMAIL_CLOUDFLARE_ACCOUNT_ID` and `EMAIL_CLOUDFLARE_API_TOKEN`; a delivered or queued receipt is accepted, a bounce or a Cloudflare suppression is refused. SMTP uses `EMAIL_SMTP_TLS` (`starttls` by default, or `tls`), `EMAIL_SMTP_HOST` (a name, never an IP literal, and never a name whose last label is all digits or any hex label, such as `2130706433`, `127.1`, `0x7f000001` or `127.0x1`), `EMAIL_SMTP_PORT` (587, or 465 for `tls`), `EMAIL_SMTP_USER` and `EMAIL_SMTP_PASSWORD`, and always requires TLS 1.2 or later with a verified certificate and forced authentication. The entry needs the optional `zod` 4.6.6 peer; SMTP also needs the optional `nodemailer` 10.1.4 peer, imported only on the first SMTP send.

Changes from the apps: `sendTransactionalEmail(message, env)` becomes `sendTransactionalEmail(message, { env, isSuppressed })`, suppression applies to every transport rather than SES only, a delivered Cloudflare receipt resolves `'unconfirmed'` instead of discover's `'provider-reported-delivered'`, and `EMAIL_TRANSPORT`, `EMAIL_SMTP_TLS`, `EMAIL_SMTP_PORT`, `EMAIL_SES_REGION` and `EMAIL_SES_CONFIGURATION_SET` now accept `_FILE` too. The application still owns its message text, the suppression list and its feedback webhook, rate limits, and what it tells the user.

Adoption checklist for each app:
- `zod` 4.6.6, and `nodemailer` 10.1.4 if it sends over SMTP, both kept in the app's own dependencies. pnpm does not install optional peers.
- `isSuppressed` at every send site. Discover has two, `account-security.ts:242` and `api.ts:138`. An app with no list passes `false`. Books gains the `ses` and `cloudflare` transports, and has no suppression list for them.
- `CONFIG_INVALID` mapped to 503, as described under Environment configuration.
- Discover's two email test changes:
  - the expected Cloudflare value becomes `'unconfirmed'`;
  - `isSuppressed` moves from the test seam to the send option.

Package tests use injected transports only. Record each consumer's imports and checks in its adoption issue.

## Hashed auth tokens and locked auth

From runtime 0.29.0, `@ten98/runtime/auth` stores session tokens and verification identifiers as keyed hashes ([#131](https://github.com/Ten98-IO-Company/ten98-code-system/issues/131)), so someone who reads the database gets no live session or reset link. It also adds `withLockedAuth`, `withLockedAuthByEmail` and the password sign-in `signInWithPassword` ([#132](https://github.com/Ten98-IO-Company/ten98-code-system/issues/132)). The entry imports its `drizzle-orm` 0.45.2 and `pg` 8.23.0 peers as well as `better-auth` 1.7.7.

**Breaking changes in 0.29.0** for an app's OIDC sign-in and schema ([#143](https://github.com/Ten98-IO-Company/ten98-code-system/issues/143); see [Linked OIDC identities](#linked-oidc-identities)):
- `auth.api.completeOidcSession` requires `provider`, the app's key for the provider configuration, beside `oidcUserId`; a call without it, or with a blank one, answers 400 and signs no one in;
- `completeOidcSession` refuses an account `isAccountUsable` refuses (by default one with `closed_at` set) with the unknown-user 401;
- the Drizzle tables the adapter uses must map `"user".closed_at` as `closedAt` and `session."oidcProvider"` as `oidcProvider` (the `user` and `session` tables of `./db` do). better-auth's own schema check refuses requests until they do, and `completeOidcSession` fails with 500 rather than skip the usability check;
- `assertSchema`, and so every locked call, requires `session."oidcProvider"` and the unique index on `account ("providerId", "accountId")`; `tokenStorageUpgradeStatements` adds the column;
- `"user".email` must be lower-case (`user_email_lowercase`); `tokenStorageUpgradeStatements` adds the constraint after its twin pre-check;
- better-auth's `/unlink-account` and `/list-accounts` answer 404;
- an app's own identity table (discover's `oidc_identity`) and session provider column (`oidcProviderId`) give way to account rows and `oidcProvider`.

**Adoption checklist for each app:**
- pass `database` as an adapter factory (`drizzleAdapter(db, { provider: 'pg', schema })`) and add `transactionDatabase: tx => drizzleAdapter(tx, { provider: 'pg', schema })`;
- run `tokenStorageUpgradeStatements` in a numbered migration (below); books also deletes its `totp-used:` rows there;
- add `oidcProvider` to the Drizzle `session` table the adapter uses, or use `session` from `./db` (also in `teamSchema`), and `closedAt: timestamp('closed_at', { withTimezone: true })` and the `user_email_lowercase` check to its `user` table, or use `user` from `./db`. Books' and discover's `user` tables do not map `closed_at` today. The common `session` table has exactly the columns, types, defaults and constraint names books', discover's and campaign's (0013) tables already have, plus `oidcProvider`; it declares no index, so each app keeps its own (`session_user_idx` and/or `session_user_active_idx`);
- compute `current` and revoke by session id, and use `/revoke-other-sessions`;
- read session and verification rows with `auth.sessionTokenKey` and `auth.storedVerificationIdentifier`;
- route password sign-in through `auth.signInWithPassword` and two-factor challenges through `auth.verifyTwoFactor(db, request)`, with the request headers (and, for sign-in, `source`, the client address the app derives with `clientLimitKey`). better-auth's own `/sign-in/email` and `api.signInEmail` are off on the instance the app holds, and it answers 404 to `/two-factor/verify-totp`, `-backup-code` and `-otp` when the request carries the challenge cookie; verification with a session (enabling two-factor) still goes to `handler`;
- give `signInWithPassword` the limiter in two steps: the per-source and per-pair limits in `source`, asked before anything touches the database, and the account-wide limit in `account`, which skips only its account-wide bucket when `knownDevice` is true;
- run `auth.assertSchema(db)` at start-up, with its errors mapped to a bare 500: it fails loudly, naming the expected and the missing tables and columns, unless `"user"`, `account`, `session` (with `oidcProvider`) and `verification` have the columns the preset uses, `account` keeps its unique index on `("providerId", "accountId")` and the user table its unique index on `lower(email)` (`user_email_normalized_idx` in workspace-team.sql). Every locked call runs the same check once, so a wrong schema is an error, never a refused sign-in. An app with other table names (campaign's `users`, `accounts`, `sessions`, `verifications`) must rename or map them first; The accepted email index is a valid, non-partial, single-column unique index that is either `lower(email)` on a text column, `lower(email::text)` on a varchar one (it prints as `lower((email)::text)`), or a plain unique index on a `citext` email column; any name is fine. A refusal is not remembered: once the index exists, the next call passes without a restart. The errors are `SchemaMismatchError` (`code: 'AUTH_SCHEMA_MISMATCH'`, with `missing`), `MissingEmailIndexError` (`MISSING_EMAIL_INDEX`) and, when a lookup still finds two accounts at one email because the index was dropped after the check, `AmbiguousAccountError` (`AMBIGUOUS_ACCOUNT`); map them to a bare 500 (sign-in answers the last as the uniform 401);
- pass `isAccountUsable` if the app marks closed or suspended accounts other than with `closed_at`; it is asked at the password check (before and under the account's lock), when a two-factor challenge completes, by `completeOidcSession` and by the preset's reset routes;
- in account closure, set `closed_at` and delete the user's sessions and all its verification rows (`DELETE FROM session WHERE "userId" = $1` and `DELETE FROM verification WHERE value = $1`), in one transaction. The preset refuses resets for an account `isAccountUsable` refuses: `/request-password-reset` answers as for an unknown email, stores no token and sends nothing, and `/reset-password` treats a token issued before closure as invalid. Deleting the rows is still the app's, and so is refusing resets in any reset route of its own;
- put `/change-password` and `/verify-password` behind the app's per-user limiter;
- count the known-device lane's `concurrency` with the shared one when sizing `UV_THREADPOOL_SIZE`;
- inside a by-id `withLockedAuth` callback, never call the team or tenancy helpers, the app's own `teams.ts` wrappers, `lockEmail` or a second `withLockedAuth`, and await every call on the bound instance;
- give the pool a `lock_timeout` (node-postgres `lock_timeout` in the pool config, below `statement_timeout`): without it, a team helper that opens its own pool connection inside a callback waits on that callback's own row lock without bound;
- treat rotating the secret as a re-enrolment event.

**Keys.** Two 32-byte keys are derived from the Better Auth `secret` with HKDF-SHA256 (empty salt), labelled `ten98-auth:verification-identifier:v1` and `ten98-auth:session-token:v1`. No new variable is needed, and the labels keep both keys apart from any other use of the same secret. Rotating the secret is a re-enrolment event, not routine operation: it ends every session, reset link and trusted device, and the enrolled two-factor secrets and backup codes, which better-auth encrypts with the same secret, become unreadable, so every user enrols a second factor again. Campaign gives Better Auth its own `AUTH_SECRET` and never rotates it.

**Session tokens.** The `session.token` column holds the handle `v1.` + base64url(HMAC-SHA256(session key, token)); the cookie keeps the raw token. Every lookup by token hashes what it is given and returns the caller's raw token, so a refresh re-sets a working cookie. A handle given back as a token is hashed again and matches nothing, so a leaked handle cannot sign in. Listings return handles: compute `current` by comparing each listed session's **id** with the current session's id, and revoke by id, one session with the app's own `DELETE … WHERE id = $1 AND "userId" = $2`, the others with `/revoke-other-sessions`. The preset replaces better-auth's version of that endpoint: it keeps the current session by id, deletes only that user's other live sessions through the adapter (inside `withLockedAuth`, in that transaction) and answers `{ status: true, revoked: <count> }`; the server call is `auth.api.revokeOtherSessions({ headers })`. `/revoke-session` given a listed handle finds nothing and fails closed. Updates and deletes pass a handle through, but better-auth 1.7.7's `deleteSession` reads the row before deleting it, so `internalAdapter.deleteSession(handle)` deletes nothing: revoke by id. A count of a user's sessions by `userId` is unchanged. The cookie cache stays off and no secondary storage is used, so tokens are kept nowhere else. Only the two-factor plugin and the preset's own two plugins run; `multi-session`, whose `deleteSessions([handle])` deletes by a listed handle, is not enabled, and a test pins that.

**Verification identifiers.** Known prefixes are kept and the rest is hashed, matched longest first: `2fa-attempts-` and `oidc-challenge:` (each names a challenge, and its rest is stored with this same rule, so a stored attempt counter is exactly `'2fa-attempts-' || <stored challenge identifier>` and a challenge's provider binding `'oidc-challenge:' || <stored challenge identifier>`), `2fa-otp-`, `2fa-`, `trust-device-` and `reset-password:`, each followed by base64url(HMAC-SHA256(verification key, rest)). Any other identifier is stored whole as `v1.` + the HMAC. Prefix `LIKE` filters (`2fa-%`, `trust-device-%`, `reset-password:%`) and the preset's own reset cleanup keep matching. The preset hashes identifiers in its adapter wrapper, not through better-auth's `verification.storeIdentifier`: in 1.7.7 a lookup under that option that finds nothing retries with the raw identifier, so a database reader could redeem a stored reset row by sending its stored tail as the token. Rows an app writes with its own SQL, such as books' `totp-used:` rows, are never touched.

**Helpers.** `auth.storedVerificationIdentifier(raw)` returns the stored identifier for a raw one, to lock or read the row with the app's own SQL, and `auth.sessionTokenKey(raw)` returns the stored handle for a raw session token (the cookie's value without its signature, as better-auth's signed-cookie reader returns it), for a guard that reads session liveness in its own statement. Both are also exported standalone as `storedVerificationIdentifier(secret, raw)` and `sessionTokenKey(secret, raw)`; prefer the methods, which keep the secret in one place.

**Upgrade.** Plain rows written before the upgrade never match again. Every app's numbered migration for the release runs exactly `tokenStorageUpgradeStatements`, which also adds the session's provider binding and the lower-case email constraint ([Linked OIDC identities](#linked-oidc-identities)):

```sql
DELETE FROM "session";
--> statement-breakpoint
DELETE FROM verification WHERE identifier LIKE 'reset-password:%' OR identifier LIKE 'trust-device-%' OR identifier LIKE '2fa-%';
--> statement-breakpoint
ALTER TABLE "session" ADD COLUMN IF NOT EXISTS "oidcProvider" text;
--> statement-breakpoint
DO $$
DECLARE twins integer; listed text;
BEGIN
  SELECT count(*), string_agg(ids, ', ' ORDER BY first) FILTER (WHERE n <= 20)
    INTO twins, listed
    FROM (SELECT '[' || string_agg(id, ', ' ORDER BY id) || ']' AS ids, min(id) AS first, row_number() OVER (ORDER BY min(id)) AS n
          FROM "user" GROUP BY lower(email) HAVING count(*) > 1) shared;
  IF twins > 0 THEN
    RAISE EXCEPTION 'user_email_lowercase: % email address(es) belong to more than one user when case is ignored (accounts: %); resolve them before this migration',
      twins, listed || CASE WHEN twins > 20 THEN ', …' ELSE '' END;
  END IF;
END
$$;
--> statement-breakpoint
UPDATE "user" SET email = lower(email) WHERE email <> lower(email);
--> statement-breakpoint
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'user_email_lowercase' AND conrelid = '"user"'::regclass) THEN
    ALTER TABLE "user" ADD CONSTRAINT user_email_lowercase CHECK (email = lower(email)) NOT VALID;
  END IF;
END
$$;
--> statement-breakpoint
ALTER TABLE "user" VALIDATE CONSTRAINT user_email_lowercase;
```

Every user signs in again, reset links in flight stop working, trusted devices ask for the second factor again, and pending two-factor challenges end (`2fa-%` also covers the `2fa-otp-` and `2fa-attempts-` rows). Rows an app writes itself are its own decision; books deletes its `totp-used:` rows in the same migration. The pre-check stops the migration while two accounts share an email ignoring case, naming their account ids grouped per address (at most 20 groups) and never an address, because the message lands in server logs; it never picks between twins, so an operator resolves them and runs the migration again. Where `user_email_normalized_idx` already exists (the common schema, and books since 0001), twins cannot exist and the check passes. An app whose session table has a provider column of its own (discover's `oidcProviderId`) drops it in the same migration; every session ends there anyway. A second run does not fail: the column is added if missing and the constraint only once. The constraint is added `NOT VALID` and then validated, so on a large `"user"` table run the `VALIDATE` statement in a migration of its own: inside the transaction that added the constraint it gains nothing, as that transaction already holds the table exclusively.

**Locked auth.** `auth.withLockedAuth(db, userId, (auth, tx) => …)` runs the callback in `transaction(db, …)` from `./db`. Its first statement sets the transaction's `lock_timeout` (`lockTimeoutMs`, 5000 by default), and its second is `SELECT id FROM "user" WHERE id = $1 FOR NO KEY UPDATE`, so foreign-key checks on the user row are not blocked. A missing user throws `LockedAuthUserNotFoundError` (`status: 404`). `auth.withLockedAuthByEmail(db, email, (auth, tx, userId) => …)`, for reset requests and other flows that know only an email, sets the timeout, takes the email advisory lock (`pg_advisory_xact_lock(109859, hashtext(email))` with the email trimmed and lowercased, the team controller's `lockEmail`; `emailLockKey` changes the first key), then locks that account's user row if there is one; `userId` is undefined when no account has the email. The callback's `auth` is a better-auth instance bound to `tx`, built per transaction (about 1 to 2 ms on PostgreSQL in measurement). Its `revokeAllSessions()` deletes the locked user's sessions in the transaction, as campaign's host CLI reset needs. When the callback throws, or the connection is lost, nothing it did persists, the callback's own error is rethrown, and Set-Cookie headers produced inside are lost with the result.

Once the callback returns, the bound instance and its `tx` are closed: a later call on either, including one the callback started and did not await, throws `LockedAuthClosedError` (`code: 'LOCKED_AUTH_CLOSED'`), and a statement on `tx` reaches no connection. Refused before any statement: a transaction passed as `db`, a database on a locked-auth connection, a second `withLockedAuth`, `withLockedAuthByEmail` or `signInWithPassword` started inside a callback (one user per transaction: it would wait on the first one's locks), and a call from inside a better-auth request or hook.

The callback's rules:
- run its own statements on `tx` (`tx.execute(sql…)` or typed queries), before and after an endpoint call, and await every call;
- take further locks only on that user's rows, in the order session, credential (account), verification, after the user row;
- never call the tenancy helpers or the workspace-level team operations (all 14 workspace, membership and invitation methods). They refuse a transaction `withLockedAuth` opened, its savepoints and its pg connection with `LockedAuthTransactionError` (`code: 'LOCKED_AUTH_TRANSACTION'`), a programming error. A transaction the helper did not open is never refused. A custom `TeamClient` wrapper around `tx` hides the connection, so pass the connection itself;
- never call `team.lockEmail` after a by-id lock: it would take the email lock after the user row, the reverse of the global order, and deadlocks (SQLSTATE 40P01) against a sign-in by email. It is refused there. Inside `withLockedAuthByEmail` it is allowed for that same email only, whose lock the transaction already holds;
- never call a helper that opens its own pool connection, such as books' and discover's `teams.ts` wrappers: that connection waits on this transaction's own row lock, which no refusal can see, and it waits without bound unless the app's pool sets `lock_timeout` (then it fails with SQLSTATE 55P03);
- never arm a timer or other deferred work inside a callback that later opens a locked-auth transaction: it inherits the callback's context, so the call is refused as nested even after the first transaction has ended (it fails closed);
- never sign in with a password inside: the bound `api.signInEmail` and `handler` on `/sign-in/email` are refused, because each attempt would hold a pool connection and the lock while it hashes (campaign measured 50 wrong guesses at one account stalling a pool of 10 for about 10 s).

**Password sign-in.** `auth.signInWithPassword(db, { email, password, source, rememberMe?, headers? }, { source, account })` is the only supported way to sign in with a password through the preset. better-auth's own password sign-in is off on the instance the app holds: `POST /sign-in/email`, in any case and with any trailing slash, answers 404 and `api.signInEmail` throws. `allowRawPasswordSignIn: true` turns it back on, without any of the checks below: do not use it outside tests and migrations. The helper returns a `Response`: the session cookie, or the two-factor challenge, as `/sign-in/email` does; the app forwards its status and Set-Cookie headers, and its body or a reduced one (the success body carries the raw session token, which page script does not need). Pass the request's headers: better-auth checks the origin only on requests it routes itself, so the helper answers 403 to an Origin other than `appUrl`'s or a cross-site or same-site `Sec-Fetch-Site` (in any case), before anything is counted. Then, in order:
1. `source({ email, source })`, the app's per-source and per-pair limits, evaluated and counted before anything touches the database: a flood the app refuses costs a counter and no pool connection, whatever cookie it carries, and per-source counting keeps one source (a flood of distinct emails, say) from filling the verification queue. `source` is required. Anything but `true` answers 429, and nothing else is asked.
2. The known-device check (below): a database read, and for a live device a claim under the account's locks, for an attempt the source step allowed only.
3. `account({ email, source, knownDevice })`, the app's account-wide limit, still before any hash or queue; with `knownDevice` it may skip its account-wide bucket. Anything but `true` answers the same 429 and gives the device's claim back. Both functions are required (a missing one is a TypeError) and may return a promise. A password longer than the policy's 128 characters then gets the uniform 401 unhashed, as no stored password can match it.
4. A slot among the process's bounded verifications (`passwordVerification`: `concurrency` 2, `queue` 100, `waitMs` 15000). With no slot in time, or the queue full, the answer is 503 with `Retry-After`; no attempt waits without bound. Two derivations per attempt fill libuv's four default threads; raise `UV_THREADPOOL_SIZE` before raising `concurrency`. An attempt whose known-device claim was verified (below) takes a reserved lane instead, `passwordVerification.knownDevices`: 1 at once and 20 waiting by default, with the same wait. Its verifications run on the same hashing threads, so count its `concurrency` in when sizing `UV_THREADPOOL_SIZE`. It uses only the lane, so a flood cannot crowd it out and a pile of valid cookies cannot take shared capacity beyond the lane's own slots. The claim is a database read checked before anything that differs between a real and an unknown account; every attempt without one (an unknown email, an account on a new device, a forged, revoked or foreign cookie) takes the shared queue under the same rule, so none can be told apart by order or by 503. During a distributed flood a user on a new device therefore still waits, or gets 503, like everyone else in the shared queue: per-source limits at the edge and an app-wide global limiter stay each app's job.
5. One short pool read of the credential; its connection is back in the pool before any hashing.
6. Both the modern and the legacy (`verifyLegacyScryptHash`) verifiers, one of them against a fixed dummy hash, outside any transaction. An unknown email, a wrong password and an account without a password all get the same 401, with the same body and headers, at the same cost.
7. Only a correct password whose account `isAccountUsable` accepts enters `withLockedAuthByEmail`; a refused one gets the uniform 401 there, before the lock, at a wrong password's cost. Under the lock: no account at that email (it moved before the lock was granted), or an account `isAccountUsable` refuses (by default one with `closedAt` set), gets the uniform 401 after the derivation a sign-in would have cost; otherwise better-auth verifies again and creates the session. A session (or two-factor challenge) for any other account than the locked one rolls the transaction back and gets the uniform 401; so does a lookup matching two accounts, which the unique index rules out. If the password changed in between, the answer is the same 401 and no session is created. With `legacyPasswords: true`, a legacy hash is replaced there, under the lock, exactly once, in a savepoint: a failed replacement leaves the sign-in standing and is retried next time. A transaction COMMIT rolled back answers 500 with no cookie.

`/change-password` and `/verify-password` check a password for a caller who already has a session, through better-auth, without the sign-in limiter or the verification queue. Put them behind the app's per-user limiter (`ten98AuthPolicy.rateLimits.accountSecurityWritesPerUser`, keyed by the session's user), as the account-security routes already are.

The limiter stays app-owned, with its own store. Campaign's keys, the pattern for the others: the client (`clientLimitKey` of the trusted address, 30) and the client and account pair (an HMAC of both, 10, cleared on a successful sign-in) in the source step, and the account (an HMAC of the email, 50) in the account step, each per 15 minutes from its first attempt. One source can lock out only its own pair. The account-wide bucket is the one a distributed attacker could hold full, so `knownDevice` lets a browser the account already signed in on skip it.

**Known devices.** After a sign-in completes (a correct password with no second factor pending, the second factor of a challenge, or `completeOidcSession` without a challenge), the preset gives the browser a known-device entry for that account; a failure, a refusal, a pending second factor, enabling two-factor and every other response issue nothing.
- **Record.** A `verification` row `known-device:<deviceId>` whose `value` is the user id and `expiresAt` 90 days on, plus one `known-device-attempt:<deviceId>` row per attempt the device has been trusted for since its last success. Both are stored hashed by the identifier rule above, with their prefixes kept, so they live in PostgreSQL, survive restarts and hold across replicas. No new column or table is needed; the upgrade statements are unchanged.
- **Cookie.** `<prefix>.known_device`, HttpOnly, Secure on https, SameSite=Lax, Max-Age 90 days. Each entry is a random 24-byte `deviceId` (it says nothing about the device) and `base64url(HMAC-SHA256(k, userId ‖ deviceId))`, `k` derived from the secret by HKDF under `ten98-auth:known-device:v1`. A browser holds one entry per account it signed in to, each with its own `deviceId`, so no identifier links one person's accounts; at most 5 entries, newest first, the oldest dropped. A missing, malformed or oversized cookie (over 1024 characters) is ignored, never an error. When a browser signs in to a sixth account, the entry it holds longest is evicted: that browser is no longer a known device of that account, whose row stays until it expires or is revoked.
- **When `knownDevice` is true.** Checked after the source step allows the attempt and before the account step: an entry's tag verifies, in constant time, for the account behind the email being tried; its device row exists, belongs to that user and has not expired; and fewer than 5 attempts are claimed since its last success. The attempt is then claimed (under the account's email and user locks, so concurrent attempts claim exactly), and given back if the account step or the verification bound refuses it before the password is checked.
- **What it exempts.** Only the account-wide bucket, and only for that account. Per-client and per-pair limits still apply, the cookie never authenticates (the password is always checked, and a wrong one is the same 401), and it never shortens another account's lockout. A stolen cookie gives an attacker five guesses past the account bucket before its trust ends, still under the per-client and per-pair limits. It also admits the attempt to the reserved verification lane described above.
- **Rotation and failures.** Each success from the browser replaces its entry: the old device row and its attempts go, a new `deviceId` gets a fresh 90 days, so a copied cookie stops working at the owner's next sign-in. After 5 wrong passwords the device counts as unknown until its next success. An account keeps at most 5 live device rows, one per browser: issuing a sixth evicts the oldest, so a browser that keeps clearing its cookie cannot pile up trusted devices.
- **Revocation.** A password change (`/change-password`), a reset, `revokeAllSessions()`, `/revoke-sessions` and `/revoke-other-sessions` delete all of that user's known-device rows, so every browser of theirs is unknown again; that covers an OIDC-only account's revoke-all too. Account closure is the app's: delete the user's rows with the rest of its verification rows (`DELETE FROM verification WHERE value = $1 AND identifier LIKE 'known-device%'`), or delete all of the user's verification rows by `value`. `/sign-out` deliberately does not forget the device: a device cookie is meant to survive sign-out, so the same browser is still known at its next sign-in. Closing an account must revoke what it still holds, in the app's closure transaction: a closed account's existing sessions keep working and refreshing, and a reset link already sent still succeeds, until they are deleted. Delete its sessions and every verification row it owns, which covers pending two-factor challenges, reset links and known devices: `DELETE FROM session WHERE "userId" = $1` and `DELETE FROM verification WHERE value = $1`. A new password sign-in, the completion of a challenge and the preset's reset routes are refused by `isAccountUsable` once `closed_at` is set; a reset route of the app's own must refuse a closed account itself.

**Account creation stays outside `withLockedAuth`**, because there is no user row to lock yet. First-user setup (books' `claimInstallation`, discover's and campaign's setup: the installation row, then `team.lockEmail`, then the user, credential, workspace, owner membership and operator rows), sign-up through an invitation (`acceptInvitation` creates the user and the credential in its own transaction) and OIDC first sign-in (`signInOidcUser`) each run in one transaction under the email lock. Because a locked-auth transaction never waits on a workspace, membership, invitation or later email lock, every wait between the two kinds of transaction runs one way and no cycle forms. The integration tests run acceptance and the two-factor requirement against `withLockedAuth` from two connections in both orders, first-user setup against a transaction by email, and the by-id `lockEmail` pairing that used to deadlock.

## Linked OIDC identities

From runtime 0.29.0, `@ten98/runtime/auth` owns the one model for an identity linked through an OpenID Connect provider ([#143](https://github.com/Ten98-IO-Company/ten98-code-system/issues/143)); no app keeps its own identity table. The app keeps its provider configurations, the OIDC protocol (discovery, the authorization request, ID token verification) and its routes, and passes the preset only claims from an ID token it verified.

**Mapping.** A linked identity is a better-auth `account` row: `providerId` is `'oidc:' + normaliseOidcIssuer(iss)` (`oidcProviderId(iss)`), `accountId` is `sub`, and `userId` the linked user. `account_providerId_accountId_key` makes (issuer, subject) unique: one account holds an identity. `accessToken`, `refreshToken`, `idToken` (and their expiry and scope columns) and `password` stay NULL on every identity row: no provider token is stored. Identities belong to the issuer, not to a provider configuration, so two configurations on the same issuer (two client ids, say) share identities.

**`normaliseOidcIssuer(issuer)`** lowercases the scheme and the host (ASCII letters only), removes an empty port (`host:`) or a default one (`:443` for https, `:80` for http) and drops one trailing slash from the path; userinfo, the rest of the path, and any query or fragment are kept exactly as given. A value with no scheme and host, a malformed host or port (a second port, a non-numeric one, an unmatched bracket) or a path ending in `//` throws a TypeError, so normalising a normalised issuer changes nothing. Every lookup, link and provisioning uses it. A subject (`sub`) is at most 255 characters, not blank and without control characters; anything else is a TypeError before any query. `normaliseOidcIssuerSql` is the same rule for a migration that copies identities into account rows: it creates the session-scoped `pg_temp.ten98_normalise_oidc_issuer(text)` (NULL where the function throws), called schema-qualified on the connection that created it, for example `INSERT INTO account(id, "accountId", "providerId", "userId") SELECT gen_random_uuid()::text, subject, 'oidc:' || pg_temp.ten98_normalise_oidc_issuer(issuer), user_id FROM oidc_identity`. The preset never rewrites stored issuers.

**Linking, strict by default.** There is no option that links automatically.
- A provider sign-in never links to an existing account. `signInOidcUser(db, claims, provider, { emailLockKey? })` resolves `{ userId, created }`: the user linked to `claims.iss` and `claims.sub`, or a new account. With no identity linked, it creates one only when the claims carry `email_verified === true` and an email, and the provider configuration the app passes has `trustVerifiedEmail: true`; otherwise it refuses with `OIDC_EMAIL_UNVERIFIED` (403). That check comes first, so an untrusted provider learns nothing about which emails have accounts. An email that already has an account is refused with `OIDC_ACCOUNT_EXISTS` (409).
- `trustVerifiedEmail` defaults to false, so adopting the preset never widens provisioning on a provider whose operator did not opt in. Discover passes its per-provider operator setting; campaign sets it on its one deployment configuration to keep provisioning on a verified email; books has no provider.
- An account is created under the shared email lock (`pg_advisory_xact_lock(emailLockKey, hashtext(email))`, the team controller's `lockEmail`, 109859 by default), like every other account-creation path, with the email lower-cased, `emailVerified` true, no password, and the claims' `name` (or the email). It takes the lock before the user row, as `withLockedAuthByEmail` does, so the two wait on each other without deadlock; it refuses a locked-auth transaction. Given the app's own transaction, it holds the lock until that commits.
- An existing account is joined in only two ways. One is accepting an invitation through the provider: `team.acceptVerifiedOidcInvitation(client, token, { email, name, issuer, subject })` requires the provider-verified email to equal the invited one (`OIDC_INVITE_EMAIL_MISMATCH`, 403) and links the identity to the account it creates, in the same transaction. An email that already has an account is refused with `OIDC_ACCOUNT_EXISTS`, and an identity another account holds with `OIDC_IDENTITY_IN_USE` (409), both before anything is written. An acceptance through a provider should always pass `issuer` and `subject` (the ID token's `iss` and `sub`). Without them it creates the account but links no identity, so that user's next sign-in through the provider finds no identity, meets the existing email and is refused with `OIDC_ACCOUNT_EXISTS` until they sign in another way and link the provider. The other is the signed-in user's own link: `linkOidcIdentity(tx, { issuer, subject })`, called inside `withLockedAuth` for that user, on its `tx`, after the app verified an ID token the user obtained while signed in. It resolves `{ linked }`, false when the identity was already this user's, and refuses one linked to another account with `OIDC_IDENTITY_IN_USE` (409). Outside a by-id `withLockedAuth` transaction (in `withLockedAuthByEmail` too) it throws a TypeError. An app offers the link only if it wants to.
- `unlinkOidcIdentity(tx, { issuer, subject }, { legacyPasswords?, isIssuerUsable? })`, inside `withLockedAuth`, deletes the identity's row. It refuses with `OIDC_LAST_SIGN_IN_METHOD` (409) when the user would be left with no way to sign in, and with `OIDC_IDENTITY_NOT_FOUND` (404) for an identity the user does not hold. Only a way that can sign in counts: a password hash the preset verifies (better-auth's; Campaign's legacy one only with `legacyPasswords: true`, as passed to `createTen98Auth`; never an empty or malformed value), or another linked OIDC identity whose issuer `isIssuerUsable(issuer)` accepts (every issuer by default, as the preset cannot know which providers the app still has configured). Account rows of any other provider do not count. It locks the user's account rows, so a concurrent change to them is counted. It does not end sessions; call `revokeAllSessions()` in the same callback where the app wants that.
- The preset turns off better-auth's own `/unlink-account` and `/list-accounts` (both answer 404): identities are linked and unlinked only through these two functions, under the user's lock.
- Every refusal is an `OidcIdentityError` with `code`, `status` and a message safe to show.
- `completeOidcSession` refuses an account `isAccountUsable` refuses (by default one with `closed_at` set) with the 401 an unknown user gets, so a closed account never signs in through a provider.
- Deleting a provider configuration deletes no identities. Sign-in through it is impossible without its client, and the rows go with unlinking or account closure.

**Session binding.** `session."oidcProvider"` (nullable text, in workspace-team.sql and the Drizzle `session` table from `./db`) holds the app's key for the provider configuration a session began through: discover's provider id, or campaign's one deployment configuration. `auth.api.completeOidcSession({ body: { oidcUserId, provider } })` requires `provider` (at most 256 characters, not blank, no control characters; 400 otherwise) and stores it. For an account with two-factor enabled, the sign-in challenge carries it in an `oidc-challenge:` verification row, and the session the challenge creates takes it. Every sign-in challenge gets that row when it is opened, empty for a password sign-in, and a challenge whose row is missing never completes (401): it was opened while its provider was being revoked. A completion that a deadlock or serialisation failure aborts answers 503 `SIGN_IN_RETRY` with `Retry-After: 1`; nothing persisted, so the client sends the same request again. `rotateVerifiedSession` and any other session created while one is current (a password change's replacement) keep the current session's binding. `getSession` returns it as `session.oidcProvider`, for RP-initiated logout and the app's security gates. It is a column of its own beside the hashed `token`, so the #131 wrapper never touches it, and no request can set it. `assertSchema` requires the column.

`revokeProviderSessions(db, provider)` ends a provider's sessions when the app disables, deletes or reconfigures it, and resolves how many ended. It deletes the sessions bound to `provider` and the two-factor challenges such a sign-in opened, with their attempt counters, so none completes into a session later, and forgets the known devices of the users whose sessions it ended. Each pass is one transaction, challenges first, so a challenge completing at the same moment either fails or commits a session the same pass deletes; a challenge being opened at that moment loses its binding and never completes. Passes repeat while one still removes something (at most 5), so a sign-in that commits during a pass is ended by the next, and a pass a deadlock or serialisation failure aborts is retried (at most 5 times); only a failure past that reaches the caller. Disable the provider first, so no new sign-in starts through it. A sign-in that passed the app's provider check before that and commits after the last pass is still bound to the provider: call `revokeProviderSessions` again once in-flight sign-ins have finished, or have the app check the provider again after `completeOidcSession`. It refuses a locked-auth transaction, which may hold only one user's rows.

**When an issuer changes.** Links keyed by the old issuer stop matching, and nothing is migrated silently. Users re-link through the signed-in `linkOidcIdentity`. Any app migration that moves identities from the old issuer to the new one is the app's: operator-confirmed, mapping old to new explicitly, and audited. The preset never rewrites issuers.

**Upgrade.** `tokenStorageUpgradeStatements` adds `session."oidcProvider"` and the lower-case email constraint `user_email_lowercase` (`CHECK (email = lower(email))`, also in workspace-team.sql and the Drizzle `user` table), after a twin pre-check and a lower-casing `UPDATE`; a second run does not fail. See [Hashed auth tokens and locked auth](#hashed-auth-tokens-and-locked-auth). Each app's bad-rows test: two case twins stop the migration with that message, a mixed-case single row is lower-cased, and after the migration a mixed-case insert is refused. Every path that writes `user.email` in books, campaign and discover already stores it lower-case.
